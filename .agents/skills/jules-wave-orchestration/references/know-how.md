# ノウハウ: Jules の癖と、仕様を書くときの注意

手順は [../SKILL.md](../SKILL.md)。ここには「なぜそうするか」「何に気をつけるか」を書く。

## 1. Jules の癖

- **Issue と PR コメントに書かれた指示しか読まない。** チャットで補足しても届かない。
- **PR タイトルとコミットメッセージの Issue 番号を間違える。** 本文の先頭行 `Closes #N` に Jules のタスク ID が入っていたこともある（末尾の `Fixes #N` は正しかった）。対処は SKILL.md §C。
- **コミットを 1 本にまとめる。** テスト先行かどうかは履歴では確かめられない。PR 本文に貼らせた「修正前の失敗出力」と、検証用 clone での再現で確かめる。
- **説明に無い削除をする。** 仕様に約束された機能、診断、テスト、ベンチマークを、コミットメッセージにも PR の説明にも書かずに消したことが 4 回あった。差分は追加だけでなく削除も読む（SKILL.md §B-3）。
- **コンパイル対象外のファイルを壊す。** `TestCases/` 配下の `.cs` は `just test` では見つからない。名前空間の混在、`ref struct` の漏れ、別ファイルの型への参照（単体では CS0246）があった。
- **仕様の文言を別の場所に当てはめる。** 例: レビューの「`_Cuda` はメンテナーが追加する」を読んで、自分で `_Cuda` のスナップショットを足した。
- **ドキュメントの数値・事実を誤る。** 例: 配列パラメータを 8 バイトと書いた（実際は 16 バイト）。説明ページの数値はコードと突き合わせる。
- **空のコミットを push する。** 👀 が付いても、`@jules` で依頼した修正が来るとは限らない。変更ファイル 0 のコミットだけが届いたことがある。
- **Jules のブランチに外部から push すると、Jules ボットが古いツリーで逆差分コミットを自動 push して巻き戻す。** `origin/main` の 173 ファイルを削除するコミットが push されたことがある。やむを得ず push するときは、先に Issue から `jules` ラベルを外し、push 後に `gh pr view <N> --json files` で変更ファイル数が増えていないか確かめる。
- **仕様に書いた分岐をそのまま実装し、到達しないコードを残す。** 例: 到達しない場合の代用値（`size = 4`）。
- **（GitHub の挙動）コミットが 1 本だけの PR をスカッシュすると、設定によっては PR タイトルではなくコミットメッセージがタイトルになる。** 今の設定では PR タイトルが使われる。

## 2. 仕様を書くときの Do

- Issue の行番号は信用せず、コードの形で探すよう書く。マージのたびに行番号がずれる。
- 同じ Wave の別 PR が触るファイルは「Do not edit X; another PR in the same wave changes it」と明記する。
- 作り直しやリファクタは、基準スナップショット（`main` で通るもの）を先にコミットさせてから置き換えさせる。
- `!` を避けた結果 null 許容の警告が出る箇所は、書き方まで指定する（例: invariant として `InvalidOperationException` を投げさせる）。
- 診断を追加・厳格化するときは、本番コードに新しい診断が出るかを先に実測し、結果を仕様に書く。
- 診断を廃止するときは、[helpers.md §5](../../gsharp-transpiler-guidelines/references/helpers.md#5-diagnostics) の廃止の形に揃えさせる。
- 2 本の PR が同じファイルの末尾に追記する場合は、衝突することと、解消の仕方（両方残す）を書く。
- 「削除するファイル・メンバー」を仕様に列挙し、それ以外を消さないよう明記する。

## 3. 仕様で明示的に禁じるもの（軽量モデルが実際にやった失敗）

- Regex で置き換えて済ませる
- Base64 デコーダを自作する
- `#error` を `IntPtr` に書き換えて黙らせる
- 本番コードから使われない API を足す
- `[Trait]` のマジック文字列
- 計画 ID をコメントに埋め込む
- 既存のコメントを削除・改変する
- 避けられる `!` を、コメントを付けて使う

## 4. Jules に任せないもの

- **大型モデル（🔴）が要る Issue**: `jules` ラベルを付けず、ローカルで大型モデルが対応する。
- **設計判断が要る部分**: 先に大型モデルが設計メモを書き、ユーザーがレビューしてから、実装だけを渡す。
- **lowering 全体や CPU スナップショットを広く触るもの**: 単独で投入する。並列では流さない。
- **CUDA スナップショットが大量に変わるもの**: Jules は `tests/Compiler/Kassyi.GSharp.Tests.Cuda/**` を編集できず、CUDA のテストも実行できない。命名や起動ラッパーのように CUDA 側を全面的に変えるものは渡さない。少しだけ変わるものは、レビューの検証用 clone でこちらが作り直す。
- **Nsight での計測**: 人間が行う。
