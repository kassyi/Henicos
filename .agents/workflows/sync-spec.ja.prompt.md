# バッチ仕様書同期プロセス (Batch Spec-to-Code Sync)

このワークフローは、コンテキストウインドウの枯渇（LLMの迷子現象）を防ぐため、指定されたフォルダ以下のソースコード（C#など）を数ファイルずつ「チャンク単位」で読み込み、仕様書（Markdown）と照らし合わせながら進捗を管理するバッチ処理プロセスです。

## 0. セッションの初期化 (Initialization)

本タスクを開始した直後に、必ず以下の初期化プロセスを実行してください。
すでに `./tmp/update-spec/sync-context.json` が存在する場合はこの手順をスキップし、`STEP 1` に進んでください。

1. ユーザーから「`src/`以下全部」のような自然言語で対象範囲の指示があった場合、それを適切なディレクトリパスやCLIコマンドの引数（例: `src/`）に変換した上で、該当範囲にあるすべての対象ソースファイル（例: `.cs`）を抽出します（`fd -e cs <変換したパス>` ツール等を使用）。指定がなければユーザーに尋ねてください。
2. ディレクトリ `./tmp/update-spec/` が存在しない場合は作成し、`sync-context.json` を以下のフォーマットで新規作成して保存します。
    ```json
    {
        "pending_targets": ["src/...", "..."],
        "completed_targets": [],
        "discrepancies": []
    }
    ```

## STEP 1: バッチ検証セッション (チャンク処理)

対象ファイルが多数に及ぶ場合は、進行状態を自己管理しながら検証を進めてください。

### 1. 実行指示

1. `./tmp/update-spec/sync-context.json` を読み込みます。
2. `pending_targets` から **必ず3〜5ファイル程度** をピックアップします。
3. ピックアップした各ソースコードファイルを `view_file` ツールで**実際に読み込んで**ください。推測で内容を判断してはいけません。
4. 読み込んだソースコードから「クラス名」「メソッドシグネチャ」「属性」「制約」などの公開APIや仕様に関わる情報を抽出し、`rg` などを使い `docs/spec/` 配下にある関連仕様書と照らし合わせます。（必ずファクトチェックを行ってください）
5. **逆方向のチェック（未実装の仕様の発見）** 同時に、そのソースコードが対象としている仕様書に記載されているが、現在の実装には存在しない「未実装の仕様や削除された機能」がないかも確認してください。
6. 仕様書と実装の間に乖離（シグネチャの変更、機能の追加・削除、制約の変更など）を発見した場合は、`discrepancies` 配列に以下の形式でJSONオブジェクトを追加します。
    ```json
    {
        "source_code_file": "src/.../Yyy.cs",
        "target_md_file": "docs/spec/.../xxx.md",
        "topic": "該当機能やAPI名 (新設機能の場合はその名前)",
        "what_is_wrong": "相違点（例: 実装で引数Aが削除されているが仕様書に残っている / 実装にメソッドBが新設されたが仕様書にない）",
        "how_to_fix": "修正指示（例: 仕様書のシグネチャから引数Aを削除する / メソッドBのセクションを仕様書に新規追加する）",
        "evidence": {
            "code_snippet": "コード上で発見された実際の実装の抜粋",
            "spec_snippet": "仕様書の現在の記載内容の抜粋 (新設機能で該当なしの場合は null)"
        }
    }
    ```
7. 検証が完了したファイルを `pending_targets` から削除し、`completed_targets` に移動させて `sync-context.json` を上書き保存します。
8. 一度ですべての `pending_targets` を処理しようとせず、必ずピックアップしたチャンクの処理とJSONの保存が終わった段階で `2. セッションの終了` に進んでください。

### 2. セッションの終了（ハンドオフ）

JSONファイルの保存が完了したら、途中の検証内容のテキストダンプなどは出力せず、以下のフォーマットに沿って**進捗をレポートする定型テキストのみ**をユーザーに出力した上で、タスクを終了してユーザーの入力を待ってください。他に追加の対話や前置きは行わないでください。

---- 出力フォーマット ----

### ⏳ 仕様書検証 進捗レポート

#### ✅ 今回検証を完了したファイル

- `src/.../Yyy.cs` (発見した差異: N件)
- `src/.../Zzz.cs` (発見した差異: 0件)

#### ⏳ 未検証のファイル (残り M 件)

- `src/...` (一部を抜粋して表示)

---

### 次のアクションを選択してください

> [!NOTE]
> **次のチャンクの検証を続ける場合**
> 引き続き残りのファイルを検証する場合は、「**続きを検証して**」または「**y**」と入力してください。

> [!TIP]
> **【推奨】仕様書のアップデート（Apply）へ進む場合**
> 残りファイルがない場合、またはここまで蓄積した差異を仕様書に反映させる場合は、「**アップデートフェーズへ進んで**」と指示してください。

---

## STEP 2: 仕様書のアップデートフェーズ (Apply)

ユーザーから「アップデートフェーズへ進んで」と指示があった場合、または `pending_targets` が空になった場合は、以下の手順および**ドキュメント更新の必須ガイドライン**に従って仕様書を更新します。

### 📝 ドキュメント更新の必須ガイドライン

- **記述言語と文体**: 仕様書のテキストは**必ず英語（English）**で、プロフェッショナルかつ中立的な文体で記述してください。
- **読者ターゲットとスコープ**: 内部の実装詳細（How）を語るのではなく、そのAPIを利用する末端の開発者が必要とする情報（BCL互換性、アーキテクチャ、言語仕様、制約条件など）に絞って記述してください。
- **コード例の必須化**: MDNやMSDNリファレンスのように、実際のユースケースに基づいた実用的なコード例（C#）を必ず伴う解説を心がけてください。

### 実行手順

1. `./tmp/update-spec/sync-context.json` の `discrepancies` リストを読み込みます。
2. 各対象ファイルに対して `replace_file_content` などのファイル編集ツールを実行し、上記のガイドラインに従って仕様書の記述を最新の実装に合わせて修正・追記します。
3. すべての更新が完了したら、「どのような乖離が発見され、どう修正したか」のサマリー（Markdown）を提示し、タスクを完了します。
