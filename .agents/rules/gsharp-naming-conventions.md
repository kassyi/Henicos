# GSharp (Henicos) Naming Conventions: GPU/C# Boundary

This rule defines the strict naming conventions for the boundary between C# code and GPU kernels (CUDA) within the Henicos project.
All future development and code generation by AI agents must strictly adhere to these conventions.

## 1. Guiding Principle (Strict PascalCase)
- In full compliance with the C# Framework Design Guidelines, **the use of snake_case containing underscores (`_`) or prefixes (such as `Kernel_`, `Device_`) is strictly prohibited**.
- The execution space (Host / Device) must be distinguished exclusively via contextual "suffixes" or structural context.

This rule covers the C# names that users write and the compiler generates for the host. The C++ names emitted into
generated device code (renamed user identifiers via `CppNameResolver`, compiler-internal `__gsharp_*` names via
`GSharpInternalNames`) are covered in [helpers.md §3](../skills/gsharp-transpiler-guidelines/references/helpers.md#3-emitting-code).

The only C# members that may contain underscores:

- **Managed runtime entry points**: the `__gsharp_*` members of `ManagedGpuContext` (`src/Core`) that the generated
  managed C# calls. Each one is registered in `src/Compiler/Kassyi.GSharp.Compiler/Resources/InternalNames.yml` with its
  `Managed:` file, keeps the spelling of the C++ prelude function when it mirrors one, and carries
  `[EditorBrowsable(EditorBrowsableState.Never)]` so users do not see it. A new one is added to the YAML first.
- **Test methods**: `<Unit>_<Condition>_<Expected>`, see [test-architecture.md](test-architecture.md) §3.9.
- **Native bindings** that keep the name of the native API they bind, generated from `src/NativeApi/*.yml`
  (`cublasCreate_v2` in `cublas_api.yml`).

Benchmark methods are not an exception: name them in PascalCase and give BenchmarkDotNet a display name with
`[Benchmark(Description = "...")]` when the report needs one.

## 2. Naming Conventions by Category

### 1. GPU Kernels (`[GpuKernel]`)
Entry point functions launched as parallel operations from the CPU (Host) side.
- **Convention**: `{OperationName}Kernel`
- **Examples**: `FloatAddKernel`, `ParallelSubKernel`

### 2. Internal GPU Device Functions (`[GpuDeviceFunction]`)
Helper functions (`__device__`) called exclusively from within GPU kernels and not directly callable from the CPU.
- **Convention**: `{OperationName}` (Bare Name)
- **Examples**: `AlignSignificand`, `Normalize`
- **Rationale**: These functions are typically encapsulated within dedicated classes such as `GpuBigFloatKernels` (e.g., `GpuBigFloatKernels.AlignSignificand`) and never exposed as public APIs. Furthermore, because caller kernels already carry the `Kernel` suffix, method name collisions will not occur.

### 3. Compiler-Generated Wrappers (for Managed Arrays)
Invocation wrappers automatically generated by the G# compiler (Source Generator) from `[GpuKernel]`.
- **Convention**: `Launch{KernelName}`
- **Example**: `LaunchFloatAddKernel`

### 4. Compiler-Generated Wrappers (for Raw Pointers / GpuBuffer)
Compiler-generated overloads accepting `IntPtr` instead of managed arrays.
- **Convention**: `Launch{KernelName}Ptr`
- **Example**: `LaunchFloatAddKernelPtr`
- **Note**: The `_Device` suffix was previously used, but has been completely deprecated and migrated to `Ptr` to strictly comply with C# design guidelines.

## 3. Anti-Patterns (Prohibited Practices)
The following patterns are subject to immediate refactoring upon discovery:
- ❌ `Kernel_FloatAdd` (Prefixes are prohibited)
- ❌ `Device_AlignSignificand` (Prefixes and underscores are prohibited)
- ❌ `LaunchFloatAddKernel_Device` (Underscores in generated code are prohibited; unified to `Ptr` via compiler's `Marshaling/WrapperEmitter.cs`)
- ❌ `AlignSignificandDevice` or `AutoPayDevice` (`Device` is discouraged even as a suffix because it reads as the noun "apparatus/machine" in English, causing semantic misinterpretation)
