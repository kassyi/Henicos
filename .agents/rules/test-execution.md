# Test Execution Rules (`just`)

> [!IMPORTANT]
> **Always run tests via `just` (or set `DiffEngine_Disabled=true` / `CI=true`).**
> `Verify` snapshot failures launch interactive diff viewers (DiffEngine) by default, which blocks headless/agent runs indefinitely. `just` disables this automatically.

| Command | Scope |
| ----- | ----- |
| `just test` | All normal tests (excluding Stress, Benchmark and GpuTrap) |
| `just test-category <Category> [args]` | One `TestCategory` enum value, e.g. `just test-category Stress` |
| `just test-differential-cpu` | Differential tests on Tests.Cpu: each kernel on the managed and native paths against the sequential C# oracle (`Category=Differential`, no GPU) |
| `just test-differential-cuda` | The same differential tests on Tests.Cuda against CUDA (uses the GPU; run through `job-queue.js run --gpu`). Long runs: `just test-stability` (`scripts/human/test-stability.js`), whose `TEST_SEED` adds one input seed per iteration |
| `just test-gpu-trap [pause_ms] [args]` | Tests.Cuda tests that raise a real GPU fault (`Category=GpuTrap`: a CUDA `trap;` in a child process) and the CUDA cells of the differential fault seeds that are a known exception divergence on CUDA (a check CUDA does not make, such as a bounds or null check of a release build, so the launch may touch an illegal address), which every other run skips (#1457). A failing CUDA thread records its error and exits without a fault (sm_70 and later): a waiter at an mbarrier exits through `__gsharp_wait_check`, and the threads of a block that waits at the grid barrier leave it and exit. A thread still traps only when the launch has no error record, when other launches hold both its own record and the shared record, or before sm_70. Sets `GSHARP_CUDA_TRAP_TESTS=1`; the children run one at a time, the recipe's pause argument (default 3000 ms) apart. Run through `job-queue.js run --gpu`. On Windows each fault logs nvlddmkm Event 153, resets the GPU engine and writes a live kernel dump, and a series of them has frozen the machine, so run it only when a change touches the device error channel or the trap path |
| `just fuzz-diff [profile] [minutes] *args` | Differential kernel fuzzer (`profile`: `M`/`managed`, `C`/`cpu` [default], or `G`/`all`; extra arguments such as `--allow-issue <n>` and `--swarm-focus <mode>` (for example `warp-shuffle`, `barrier`, `iterator`, `suspending-call`, `split-points`) are passed to `fuzz-differential.js`; wraps GPU execution in `gpu-lock.js`) |
| `just test-memory <project> [args]` | One run of a test project with the memory report, `dotnet-counters` and a gcdump at the end; prints the peak, the tests that raised it and the types left on the heap (see Memory budgets) |
| `just coverage-diff [base]` | `just test` with coverage, then the lines changed since `base` (default `main`) that no test executed |
| `just mutate [gpumath\|compiler\|compiler-cuda] [since]` | Stryker.NET mutation test of the host code (`gpumath`: `Kassyi.GSharp.Stdlib.GpuMath`, `compiler`: `Kassyi.GSharp.Compiler` with `Tests.Cpu` minus the Differential tests that only run kernels generated at build time and so execute no compiler code (the ones that run the generator in process, `SpillOrderMutatingGetterTests` and `MathDifferentialTests`, stay), `compiler-cuda`: the files of the same compiler that branch on the CUDA dialect, with the `Tests.Cuda` snapshots; Tests.Cpu already kills most mutants elsewhere), optionally only the files changed after `since`. Runs for hours and uses the GPU (`gpumath`); report in `tmp/stryker/<phase>`. Stryker does not write the AOT artifacts under `obj/` (generator-invariants §7), so the build is usable after the run as it is. The test host heap is capped at `mutate_heap_limit` of the justfile, 8 GB (`GSharpTestHeapHardLimit`, in bytes; set it to override), so a mutant that allocates without bound fails its tests instead of exhausting memory |

The machine and its GPU are shared by every agent and worktree: run every build and test command through the job queue (`node scripts/human/job-queue.js run [--gpu] -- "<command>"`, see Job queue below). The `just` recipes above queue themselves.

A test that raises a real GPU fault carries `[Category(TestCategory.GpuTrap)]`, runs its launch in a child process (`CudaTrapRuns.RunIsolated`, or `CudaTrapGate.RunPaced` around the start of the child) and skips unless `GSHARP_CUDA_TRAP_TESTS=1`, so `just test`, CI and a plain `dotnet test` raise no fault. A differential case keeps its fault seeds in the default run; a CUDA cell that is a known exception divergence is skipped, and the report lists those seeds. A test that expects a CUDA device error that does not trap (the other differential fault seeds included) runs in the test host, in `[Collection(TestCollections.DeviceExclusive)]`: the process has one device error slot, so the error of a test running beside another one could be thrown by the other test's synchronization.

Kernel pools after GPU faults on Windows: a plain CUDA program whose kernel ends in `trap;` grew the nonpaged pool by 474 MB and the paged pool by 1,098 MB over 200 runs (unevenly), and the pools were not freed when the processes exited, only by a reboot; over nine days of test runs on the same machine (about 10,600 Event 153 entries) the pools reached 8.3 GB nonpaged and 11.1 GB paged, and a reboot returned them to 1.8 GB and 2.1 GB. Whether the driver or the live kernel dump that Windows writes per fault holds the memory is open, and faults on an illegal address were not measured (NVIDIA bug 7077284, https://developer.nvidia.com/bugs/7077284 , needs an NVIDIA developer login). A plain CUDA trap logs one nvlddmkm Event 153 entry; a G# test process logs two per fault. `gpu-lock.js` reads the pools and the Event 153 entries while the command starts and before it releases the lock (`scripts/human/gpu-fault-watch.js`, about 0.1 s each), prints them with the entries of the run, appends them to `tmp/gpu-pool-log.tsv` of the main checkout, and warns when the nonpaged pool is above 6 GB before the run or the pools grew by more than 1 GB; `GSHARP_GPU_POOL_WATCH=0` turns it off. `just test-stability` and `just long-checks` write the same readings into their summaries. When the warning suggests a reboot, tell the user, and do not start another run that faults.

Test assemblies discard console output (`TestConsole.Silence()`); set `GSHARP_TEST_VERBOSE=1` to see `Logger` / benchmark output.

Pick the command matching the domain you modified. Methodology (TDD, snapshot hierarchy) lives in [test-architecture.md](test-architecture.md).

## Job queue

The machine is shared by every agent and worktree. Run every build and test command (`dotnet build`, `test`, `msbuild`, `publish`, `pack`, `vstest`, `stryker`, `watch`, the `just` test, fuzz, mutate and benchmark recipes, the long test scripts) through the job queue:

```sh
node scripts/human/job-queue.js run -- "<command>"
node scripts/human/job-queue.js run --gpu -- "<command>"   # uses the GPU
node scripts/human/job-queue.js run --after <id> -- "<command>"   # starts once job <id> has ended, if it succeeded
node scripts/human/job-queue.js status                      # running and waiting jobs: ids, jobs ahead, expected times
node scripts/human/job-queue.js status <id> --json          # one job: state, ahead, startAt, endAt (ms since epoch)
node scripts/human/job-queue.js wait <id>                   # until it ends: exit 0 ok, 1 failed, 4 cancelled, 5 lost
node scripts/human/job-queue.js move <id> --first           # a waiting job goes first (also --before <id>, --reset)
node scripts/human/job-queue.js set-weight <id> <n>         # the slots a waiting job takes
node scripts/human/job-queue.js cancel <id>                 # one job: leaves the queue or is stopped
node scripts/human/job-queue.js cancel-all                  # every job the scheduler knows
```

The `just` recipes that build, test, fuzz, mutate or benchmark (`just test`, `just test-category`, `just fuzz-diff`,
`just bench`, ...) run their command through the queue themselves, with `--gpu` where the command uses the GPU, so a
person can run them as they are. An agent's `run -- "just test"` works as well: the recipe's own `run` finds the job it
runs in and takes no second slot. A recipe with `--gpu` still takes the GPU lock there, while the outer job holds its
slots, so queue such a recipe with `run --gpu -- "just test"`: the lock is then taken first and the recipe starts at once. The hook still asks agents to write the `run` themselves, since a worktree on an older
branch has recipes that do not queue.

- `run` prints `queued #<id>: <n> ahead, expected start ~hh:mm (in <m>m), expected end ~hh:mm` as soon as the scheduler took the job; keep the id to ask `status <id>` later (it exits 1 once the job has ended). Ids count up and are not reused while `tmp/job-queue` lives. The expected times play the queue forward with each command's typical run time, recorded per command text in `tmp/job-queue/history.json` (a command never run before counts as one minute), so they are estimates. Only runs that ended by themselves are recorded, not cancelled ones, those of a lost client, or one a signal stopped (on Windows a command ended by `taskkill /F` exits with 1 and is recorded like a failure).
- Steps that belong together (a build and the test run of what it built) go into one job as one quoted string, `run -- "dotnet build X && dotnet test X --no-build"`: the job takes its slots once and keeps them to the end, so no other job runs between the steps and nothing waits twice; it takes the memory budget of its test run, and its recorded run time is that of the whole string.
- Order: a short job goes first and a long one rises the longer it waits (response ratio, `(waited + typical run time) / typical run time`), so that none starves. A later job may also start in free slots when it does not delay the first one: it ends before the first job could start, counting every running job at its longest recorded time, or it fits in the slots the first job leaves free. `--policy backfill` (arrival order with that) and `--policy fifo` (strict arrival order) exist for comparison; the scheduler keeps the policy it was started with.
- Manual order: `move <id> --first` puts a waiting job ahead of every other (a later `--first` goes ahead of an earlier one; a job placed `--before` it stays right in front of it), `move <id> --before <other>` right in front of another waiting job wherever that one is in the order (a chain keeps its order; a cycle is refused), `move <id> --reset` back to the policy order. Backfilling still reserves the start of the first job, so a moved wide job is not delayed by smaller ones. `set-weight <id> <n>` changes the slots a waiting job takes (a running job keeps its weight, since its node limit is fixed). Both act on waiting jobs only.
- Being called when a job ends: `wait <id>` blocks until the job has ended and exits with its outcome (0 succeeded, 1 failed, 4 cancelled, 5 lost: its client died and the result is unknown; 2 for an id the scheduler does not know; `--json` prints `{id, outcome}`). It keeps waiting across a scheduler restart and answers at once for a job that already ended. Run it in the background (the background option of the Claude Code Bash tool, an Antigravity background command): the tool calls the agent when it exits, also for a job another agent or a person queued.
- Dependencies: `run --after <id>` starts only once job `<id>` has a recorded outcome that lets it run: succeeded, or any outcome with `--keep-if-failed`. The scheduler grants on that record alone, never because the other job is gone. Waiting this way does not hold up the jobs behind it, and the expected start counts from the other job's expected end. When that job failed (a non-zero exit code or a signal), was cancelled, or its client was lost, this job is cancelled too and `run` exits with 4, and so are the jobs that wait for it in turn. A job that ended earlier is judged by its recorded outcome (the scheduler keeps the last 500, also across a restart); an id it never knew is a usage error (exit 2), except in the first 1.5 s after the scheduler started (a run that started it), when the id is accepted and then counts as lost (exit 4); a predecessor the scheduler loses track of (its record dropped) counts as lost too. A client sends "done" when its command ends and waits for the scheduler's receipt; without one (the scheduler was stopping) it reports the outcome to the next scheduler. With `--gpu`, the turn at the GPU waits for the other job the same way. `--after` inside a queued job or inside the GPU lock is refused: waiting for another job while holding slots or the lock could deadlock. A job run by a client of an older checkout reports no exit code, so a job `--after` it is cancelled (its outcome counts as lost) unless `--keep-if-failed`.
- Placements, weights and dependencies survive a scheduler restart: the scheduler tells each client its new placement, and the client brings it along when it queues again. The state file also keeps the ids of the jobs that had not ended, and the next scheduler waits up to 60 s for them to come back (they hold no slots meanwhile); a dependent that returns first keeps waiting, since its predecessor has no outcome yet, and a client whose command ended while no scheduler listened reports the outcome to the next one. A job that does not come back within 60 s counts as lost. The scheduler saves its state by writing a temporary file and renaming it over the old one, and stops saving once it is told to stop, so that the next scheduler never reads half a file or has its state overwritten.
- How the scheduler decides: every event (a message, a closed connection, a timer) only changes the jobs; at its end one step cancels the jobs whose predecessor did not succeed (along chains), grants the slots and GPU turns once, and saves the state. Nothing is granted while an event is still changing the jobs.
- The queue grants slots of a CPU pool and runs the command in the current directory once granted, so incremental builds keep working. The defaults follow the machine: one slot per 3 cores, at least 2 (`GSHARP_JOB_QUEUE_SLOTS` or `serve --slots` overrides it). Every job takes 1 slot (`--weight <n>` overrides it). A test run (`dotnet test`, the `just` test recipes, the long test scripts) also takes a memory budget from a memory pool of half the physical memory (`GSHARP_JOB_QUEUE_MEMORY_MB`, `serve --memory-mb`): the budget in `tests/memory-budgets.yml` of the test assemblies its command names (the stress budget when it names `Stress` or `Benchmark`), or the sum of every budget when it names none (a run of the whole solution starts its test hosts side by side). A test run waits while its budget does not fit beside those of the running jobs; one larger than the pool runs when no other job holds memory. Builds take no memory from the pool. Measured on a 24-core machine with 64 GB (a mix of 4 forced rebuilds and 4 test runs of Tests.Cpu, two rounds each): 8 slots with test runs of 1 slot finished in 518 s on average, 6 slots with 1 slot in 555 s, 8 slots with test runs of 2 slots in 587 s and 6 slots with 2 slots, the earlier default, in 676 s at 76% CPU; each test run took about its budget in memory. `status` shows the memory in use and each test run's budget. A granted job gets cores / slots * weight MSBuild nodes: `-m:<n>` is added to each `dotnet build` / `test` / `msbuild` / `publish` / `pack` of the command that sets no `-m` of its own (also when a `just` recipe queues its command inside the job), and `GSHARP_JOB_QUEUE_MSBUILD_ARGS` carries it to other callers. Scripts that start `dotnet` themselves (`test-stability.js`, `long-checks.js`) are not limited that way; give them a larger `--weight`.
- `--gpu` first waits in the scheduler for its turn at the GPU: the turns go one at a time, in the same order as the slots (response ratio, `move`, `--after`), only while no job holds the GPU, and a waiting turn takes no slots, shows in `status` (`gpu-turn`) and can be cancelled. Once its turn came, the job takes the GPU lock (`gpu-lock.js`, which waits for `tmp/gpu-test-lock` only while a run outside the queue holds it, and reads the kernel pools), and the command under the lock registers its CPU slots as a GPU holder, granted at once, even over the pool, so a job that holds the GPU never waits for a CPU slot and cannot deadlock with a job that holds a slot and waits for the GPU. (The lock alone gave the GPU to whichever waiter polled first, so a job could be passed for an hour.) A scheduler of an older checkout has no turns; `run --gpu` then waits for the lock directly, as before. Any command that uses the GPU (`just test-category Runtime`, a `dotnet test` of a GPU suite, a benchmark) runs with `--gpu`; `gpu-lock.js` alone is no longer called directly. `just fuzz-diff`, `just long-checks` and `fuzz-differential.js` take the GPU lock themselves for their GPU steps: queue them without `--gpu` (`run --gpu` refuses them), or the inner lock waits forever for the outer one. `gpu-lock.js` sets `GSHARP_GPU_LOCK_HELD` for the command it runs, and a `run --gpu` inside it (a `just` recipe that `long-checks.js` runs under the lock) does not take the lock again. Every `run` inside such a command, with `--gpu` or not, counts as the GPU holder's job and is granted at once, like the jobs of `--gpu`.
- A slot follows the command: when the client is killed but its command runs on (a tool timeout that kills only the client), the scheduler keeps the slot until no process of the command is left. A cancelled job exits with 4 once its command has stopped; its slot is held until then. After a scheduler restart, running jobs re-register first and nothing is granted for the first 1.5 s; jobs keep their ids, so a `cancel <id>` read from an earlier `status` never hits another job, and `cancel` reports only the jobs it really cancelled (not one that ended meanwhile).
- The scheduler (127.0.0.1:47117, log `tmp/job-queue/server.log` of the main checkout, also its working directory) starts on the first `run` and exits after 30 idle minutes. On Windows it is started through WMI, outside the caller's job object: Antigravity ends every process of a command when the command ends, which would take a scheduler started as a plain child with it. `job-queue.js stop` stops it; running jobs keep running and re-register, and the next client to connect starts the next scheduler from its own checkout, so after a change to the script, stop it from a checkout with the new version and run a job from there first. A job whose client was already lost is restored from `jobs-<port>.json` next to the log. Clients and schedulers of different checkouts work together for plain runs (protocol 2); `move`, `set-weight`, `--after` and a moved job need a scheduler of protocol 3, and an older one refuses them with a message to stop it.
- `cancel-all` reaches every job the scheduler knows, `--gpu` jobs waiting for their turn included. A run of `gpu-lock.js` outside the queue (`just fuzz-diff`, `just long-checks`) is not a job: stop it with Ctrl+C or by its process.
- The command runs in the shell `run` is called from, so write it as for that tool: Git Bash on Windows when `MSYSTEM` or `SHELL` is set (the Claude Code Bash tool), PowerShell otherwise on Windows (the Claude Code PowerShell tool, Antigravity; a quoted program path needs `&`), `/bin/sh` elsewhere. `--shell bash|pwsh|powershell|cmd|sh` chooses one. PowerShell passes the exit code of the last native program on. Pass the command as one quoted string; several words after `--` are taken as arguments already split by your shell and are quoted again one by one, so `&&`, pipes and redirections among them are not shell syntax. Limits of that re-quoting: cmd still expands `%VAR%` inside quotes, PowerShell cannot pass a literal `--%` on (`run` stops with a usage error), and Windows PowerShell 5.1 (used only when PowerShell 7 is missing) drops embedded `"` from arguments.
- A command run by a queued job that calls `run` again runs at once, without a second slot, with the same node limit.
- A PreToolUse hook (`check-queued-command.js`) denies these commands when they do not go through the queue, in Claude Code (`.claude/settings.json`) and in Antigravity (`.agents/hooks.json`). Text that only names such a command passes when it is quoted or in a heredoc; the hook reads quotes as the tool's shell does (Git Bash for the Claude Code Bash tool, PowerShell for its PowerShell tool and for Antigravity), and a `$( )` or PowerShell `@( )` substitution or `$x = dotnet test` is a command. It also sees through `wsl`, `cmd /c`, `pwsh -Command`, `bash -c` and programs that run a command given in their arguments (compute-sanitizer, valgrind, a program held in a variable); `just --dry-run`, `--help` / `--dry-run` of the scripts and `gpu-lock.js --lock-path` pass. It cannot see a command held in a variable and run later, or the contents of a script file. Other agents follow this section.
- A wait can be long; run a queued command in the background when the tool has a time limit.

## Memory budgets

Every test assembly has a memory budget for its whole test host in `tests/memory-budgets.yml`. The watchdog of
`Kassyi.GSharp.Tests.Infrastructure` (`MemoryBudget`) runs in every test host and samples the peak memory of the process
every 250 ms and at the start and end of every test: the peak private memory (commit charge) on Windows, the peak
resident memory (`VmHWM`) on Linux. Native allocations count.

- **Two budgets per assembly**: `<test project name>: <MB>[, stress <MB>]`, one line per test project at column 0
  (`MemoryBudgetFileTests` fails when a test project has no line or a line names no test project). The first value
  holds for a run without Stress and Benchmark tests (`just test`); the `stress` value takes over when the first test
  with `[Category(TestCategory.Stress)]` or `[Category(TestCategory.Benchmark)]` starts (the CI filter
  `Category!=GpuExecution` runs them). The build configuration does not change the peaks measurably, so it does not
  select a budget.
- **Breach**: every test that was running when the peak passed the budget fails with `MemoryBudgetExceededException`.
  The message gives the peak, the budget and its profile, the running tests (one of them caused the growth), the five
  tests that raised the peak most (growth of the high-water mark between their start and end; approximate while tests
  run in parallel) and the memory snapshot taken at the breach.
- **Snapshot at the breach**: `dotnet-gcdump collect` of the test host plus its `dotnet-gcdump report` (types by size),
  run one-shot through `dotnet dnx` at a pinned version, into `tmp/test-memory/<assembly>-<time>-<pid>/`.
  `GSHARP_TEST_MEMORY_DUMP=full` writes a full dump (`dotnet-dump collect --type Full`) instead; `none` writes nothing.
  A tool that fails or does not finish in time is named in the message; the failing test waits at most about three
  minutes for it.
- **Final check**: `MemoryBudgetFinalCheck.WholeRunPeak_StaysWithinBudget`, compiled into every test assembly, runs
  after every other test (a `DisableParallelization` collection, ordered last by `MemoryBudgetCollectionOrderer`) and
  fails when the peak of the run passed the budget, also between tests (fixtures, disposal). A run filtered to some
  categories skips it unless the filter keeps `Category=Unit`.
- **Backstop**: `tests/Directory.Build.props` caps the managed heap at twice the larger budget
  (`System.GC.HeapHardLimit`). `GSharpTestHeapHardLimit` set from outside (`just mutate`) takes precedence. Under the
  limit, `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes` is the limit, not the machine: a test that checks the
  machine's free memory uses `ProcessMemory.ReadAvailablePhysicalBytes()`.
- **Dead hosts**: the `just` test recipes and CI pass `--blame-crash --blame-crash-dump-type mini`, so a host that dies
  (for example at the heap limit) leaves a mini dump under its `TestResults` directory. CI uploads `tmp/test-memory/`
  and those dumps as the `memory-diagnostics-<os>-<suite>` artifact when a job fails.
- A breach is a finding, not a number to raise: find the test that grew and fix the growth. Raise a budget only when the
  growth is intended, and say why in the PR.

To look into one suite: `just test-memory <project> [-c <configuration>] [--filter <expr>]`
(`scripts/human/test-memory.js`) runs it once with the report on and no budget, samples the host with `dotnet-counters`,
takes a gcdump at the end of the run and prints the peak, the tests that raised it, the counter maxima and the types
left on the heap. Run GPU suites through `job-queue.js run --gpu`.

To measure and update the budgets: set `GSHARP_TEST_MEMORY_REPORT=<dir>` (under `tmp/`) and
`GSHARP_TEST_MEMORY_BUDGET_MB=1000000` (no breach); each test host appends
`<peak MB>\t<GC heap peak MB>\t<budget MB>\t<tests run>\t<profile>\t<metric>` to `<dir>/<assembly>.tsv`, and its top
growth to `<assembly>.top.tsv`, when its final check runs. Run the suite three times each on Windows as `just test` and
as CI runs it (`-c Release --filter "Category!=GpuExecution"` with `GSHARP_TEST_NO_CUDA=1`), and on Linux (WSL) as CI
runs it. Per assembly, the first budget is 1.2 times the largest peak of the `default` profile lines and the `stress`
budget 1.2 times the largest peak of the `stress` lines, each rounded up to a multiple of 64 MB.
`GSHARP_TEST_MEMORY_BUDGET_MB` alone replaces both budgets of every assembly of the run.

## CI (GitHub Actions)

`.github/workflows/gpu-tests.yml` ("Hybrid CI") runs the tests without CUDA on GitHub-hosted runners. The repository is public, so these runners have no minute limit.

- **Ubuntu** and **Windows** run side by side for every pull request (every base branch, so a stacked PR is tested too) and every push to `main`. A failure on one OS does not cancel the other.
- Each OS runs three jobs in parallel, each building only what it tests: `Tests.Cpu`, `Tests.Cuda` and `Other tests` (every other project of the solution, including the Integration tests). Every job uploads its `.trx` files as `test-results-<os>-<suite>` (kept 7 days); `node scripts/human/ci-test-durations.js <dir>` lists the slowest tests, classes and collections from them.
- A new run for the same pull request cancels the one still running. A change to `docs/**`, `.agents/**` or Markdown files alone runs nothing.

What an agent does:

- An agent reviews every pull request and posts the review as one comment ([pr-review-pairing](../skills/pr-review-pairing/SKILL.md)). The review starts with `git merge-tree --write-tree origin/<base> origin/<head>` and `gh pr checks <n>`; a conflict or a failing check is a blocking item. After posting it, the agent adds the `agent-reviewed` label.
- The user samples pull requests and adds the `human-reviewed` label to the ones they reviewed themselves. A pull request whose description marks a breaking change, or whose review raises a question of the semantics charter, waits for the user before it is merged.
- When a pull request carries either label, read every review comment (`gh pr view <n> --comments` and `gh api repos/<owner>/<repo>/pulls/<n>/comments`), reply on the pull request with a decision per item (fixed here, or filed as an issue with its milestone), make the fixes, and push them.
- A pull request is ready to merge when it carries `agent-reviewed` or `human-reviewed`, every review item is fixed or filed, and both its Ubuntu and Windows runs are green. The agent then merges it.
- When you hand the user a merge order, list only pull requests whose runs are green on both OS, or say which ones still wait for them.
- Do not close and reopen a pull request to start CI again; it does not always pick up a newer `main`. To test against a newer `main`, push one merge of `main` into the branch. Re-running from the Actions page reuses the old merge.
- If the run on a push to `main` fails, fix `main` first.
