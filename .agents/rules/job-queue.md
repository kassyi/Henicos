# Job queue

The machine is shared by every agent and worktree. Run every build and test command (`dotnet build`, `test`, `msbuild`, `publish`, `pack`, `vstest`, `stryker`, `watch`, the `just` test, fuzz, mutate and benchmark recipes, the long test scripts) through the job queue:

```sh
node scripts/human/job-queue.js run -- "<command>"
node scripts/human/job-queue.js run --gpu -- "<command>"   # uses the GPU
node scripts/human/job-queue.js run --after <id> -- "<command>"   # starts once job <id> has ended, if it succeeded
node scripts/human/job-queue.js status                      # running and waiting jobs: ids, jobs ahead, expected times
node scripts/human/job-queue.js status <id> --json          # one job: state, ahead, startAt, endAt (ms since epoch)
node scripts/human/job-queue.js status --watch              # live view for a person (just queue-watch), in a terminal
node scripts/human/job-queue.js wait <id>                   # until it ends: exit 0 ok, 1 failed, 4 cancelled, 5 lost
node scripts/human/job-queue.js move <id> --first           # a waiting job goes first (also --before <id>, --reset)
node scripts/human/job-queue.js set-weight <id> <n>         # the slots a waiting job takes
node scripts/human/job-queue.js start <id>                  # a waiting job starts now, over the pool (a person's call)
node scripts/human/job-queue.js cancel <id>                 # one job: leaves the queue or is stopped
node scripts/human/job-queue.js cancel-all                  # every job the scheduler knows
```

The `just` recipes that build, test, fuzz, mutate or benchmark (`just test`, `just test-category`, `just fuzz-diff`,
`just bench`, ...) run their command through the queue themselves, with `--gpu` where the command uses the GPU, so a
person can run them as they are. An agent's `run -- "just test"` works as well: the recipe's own `run` finds the job it
runs in and takes no second slot. A recipe with `--gpu` still takes the GPU lock there, while the outer job holds its
slots, so queue such a recipe with `run --gpu -- "just test"`: the lock is then taken first and the recipe starts at once. The hook queues a recipe for Claude Code only with the
options the recipe itself passes to the queue (see the hook below), since a worktree on an older branch has recipes
that do not queue.

- `run` prints `queued #<id>: <n> ahead, expected start ~hh:mm (in <m>m), expected end ~hh:mm` as soon as the scheduler took the job; keep the id to ask `status <id>` later (it exits 1 once the job has ended). Ids count up and are not reused while `tmp/job-queue` lives. The expected times play the queue forward with each command's typical run time, recorded per command text in `tmp/job-queue/history.json` (a command never run before counts as one minute), so they are estimates. Only runs that ended by themselves are recorded, not cancelled ones, those of a lost client, or one a signal stopped (on Windows a command ended by `taskkill /F` exits with 1 and is recorded like a failure).
- Steps that belong together (a build and the test run of what it built) go into one job as one quoted string, `run -- "dotnet build X && dotnet test X --no-build"`: the job takes its slots once and keeps them to the end, so no other job runs between the steps and nothing waits twice; it takes the memory budget of its test run, and its recorded run time is that of the whole string.
- Order: a short job goes first and a long one rises the longer it waits (response ratio, `(waited + typical run time) / typical run time`), so that none starves. Two fairness rules then reorder that list. Round-robin: the jobs are taken worktree by worktree in turn (the worktree is the root of the job's directory, `git rev-parse --show-toplevel`, resolved once by the client), one job per worktree per round, the worktree served longest ago first, so that one chat that queues many jobs gets one turn per round; within a worktree the ratio order holds, and the CPU slots and the GPU turns rotate separately (the rotation is kept in memory and starts afresh after a scheduler restart). Bound on the wait: a job that has waited longer than max(10 minutes, its typical run time) goes ahead of every job that has not, oldest first, for slots and GPU turns alike (a long GPU job is no longer passed by a stream of short ones). A later job may also start in free slots when it does not delay the first one of that order: it ends before the first job could start, counting every running job at its longest recorded time, or it fits in the slots the first job leaves free. `--policy backfill` (arrival order with that) and `--policy fifo` (strict arrival order) exist for comparison, without the round-robin and the bound; the scheduler keeps the policy it was started with.
- Manual order: a manual place is a person's call and goes ahead of the round-robin and the bound. `move <id> --first` puts a waiting job ahead of every other (a later `--first` goes ahead of an earlier one; a job placed `--before` it stays right in front of it), `move <id> --before <other>` right in front of another waiting job wherever that one is in the order (a chain keeps its order; a cycle is refused), `move <id> --reset` back to the policy order. Backfilling still reserves the start of the first job, so a moved wide job is not delayed by smaller ones. `set-weight <id> <n>` changes the slots a waiting job takes (a running job keeps its weight, since its node limit is fixed). `start <id>` grants a waiting job at once, beside the running ones, over the slots and the memory pool as a GPU holder is (`s` in `status --watch`); it is for a person who wants one job now, and refuses a job waiting for the GPU (one at a time: `move <id> --first` puts it next), a job whose client is away (its connection dropped or the scheduler restarted: nobody would receive the grant) or one waiting for its `--after` job. All three act on waiting jobs only.
- Being called when a job ends: `wait <id>` blocks until the job has ended and exits with its outcome (0 succeeded, 1 failed, 4 cancelled, 5 lost: its client died and the result is unknown; 2 for an id the scheduler does not know; `--json` prints `{id, outcome}`). It keeps waiting across a scheduler restart and answers at once for a job that already ended. Run it in the background (the background option of the Claude Code Bash tool, an Antigravity background command): the tool calls the agent when it exits, also for a job another agent or a person queued.
- Dependencies: `run --after <id>` starts only once job `<id>` has a recorded outcome that lets it run: succeeded, or any outcome with `--keep-if-failed`. The scheduler grants on that record alone, never because the other job is gone. Waiting this way does not hold up the jobs behind it, and the expected start counts from the other job's expected end. When that job failed (a non-zero exit code or a signal), was cancelled, or its client was lost, this job is cancelled too and `run` exits with 4, and so are the jobs that wait for it in turn. A job that ended earlier is judged by its recorded outcome (the scheduler keeps the last 500, also across a restart); an id it never knew is a usage error (exit 2), except in the first 1.5 s after a scheduler started without a current state file (a run that started it), when the id is accepted and then counts as lost (exit 4); a predecessor the scheduler loses track of (its record dropped) counts as lost too. A lost predecessor cancels its dependents only once "lost" is final: while the lost job's client process still exists, it may still report how the command ended, so its dependents and `wait` keep waiting, at most 60 s. A client sends "done" when its command ends and waits for the scheduler's receipt; without one (the scheduler was stopping) it reports the outcome to the next scheduler. With `--gpu`, the turn at the GPU waits for the other job the same way. `--after` inside a queued job or inside the GPU lock is refused: waiting for another job while holding slots or the lock could deadlock. A job run by a client of an older checkout reports no exit code, so a job `--after` it is cancelled (its outcome counts as lost) unless `--keep-if-failed`.
- Placements, weights and dependencies survive a scheduler restart: the scheduler tells each client its new placement, and the client brings it along when it queues again. The state file also keeps every job that had not ended: the next scheduler restores them at once, running jobs with their slots and waiting jobs with their place (not granted until their client is back); a dependent that returns first keeps waiting, since its predecessor has no outcome yet, and a client whose command ended while no scheduler listened reports the outcome to the next one. A job whose client does not come back within 60 s, or whose client process is gone, counts as lost. The scheduler saves its state by writing a temporary file and renaming it over the old one, and stops saving once it is told to stop, so that the next scheduler never reads half a file or has its state overwritten.
- How the scheduler decides: every event (a message, a closed connection, a timer) only changes the jobs; at its end one step cancels the jobs whose predecessor did not succeed (along chains), grants the slots and GPU turns once, and saves the state. Nothing is granted while an event is still changing the jobs.
- The queue grants slots of a CPU pool and runs the command in the current directory once granted, so incremental builds keep working. The defaults follow the machine: one slot per 3 cores, at least 2 (`GSHARP_JOB_QUEUE_SLOTS` or `serve --slots` overrides it). Every job takes 1 slot (`--weight <n>` overrides it). A test run (`dotnet test`, the `just` test recipes, the long test scripts) also takes a memory budget from a memory pool of half the physical memory (`GSHARP_JOB_QUEUE_MEMORY_MB`, `serve --memory-mb`): the budget in `tests/memory-budgets.yml` of the test assemblies its command names (the stress budget when it selects `Stress` or `Benchmark` tests; a filter such as `Category!=Stress` does not), or the sum of every budget when it names none (a run of the whole solution starts its test hosts side by side). A test run waits while its budget does not fit beside those of the running jobs; one larger than the pool runs when no other job holds memory. Builds take no memory from the pool. Measured on a 24-core machine with 64 GB (a mix of 4 forced rebuilds and 4 test runs of Tests.Cpu, two rounds each): 8 slots with test runs of 1 slot finished in 518 s on average, 6 slots with 1 slot in 555 s, 8 slots with test runs of 2 slots in 587 s and 6 slots with 2 slots, the earlier default, in 676 s at 76% CPU; each test run took about its budget in memory. `status` shows the memory in use and each test run's budget. A granted job gets cores / slots * weight MSBuild nodes: `-m:<n>` is added to each `dotnet build` / `test` / `msbuild` / `publish` / `pack` of the command that sets no `-m` of its own (also when a `just` recipe queues its command inside the job), and `GSHARP_JOB_QUEUE_MSBUILD_ARGS` carries it to other callers. Scripts that start `dotnet` themselves (`test-stability.js`, `long-checks.js`) are not limited that way; give them a larger `--weight`.
- `--gpu` first waits in the scheduler for its turn at the GPU: the turns go one at a time, in the same order as the slots (response ratio, round-robin across worktrees, the bound on the wait, `move`, `--after`), only while no job holds the GPU, and a waiting turn takes no slots, shows in `status` (`gpu-turn`) and can be cancelled. `cancel` of the GPU holder cancels the `--gpu` run that started it too (both ids are listed). Once its turn came, the job takes the GPU lock (`gpu-lock.js`, which waits for `tmp/gpu-test-lock` only while a run outside the queue holds it, and reads the kernel pools), and the command under the lock registers its CPU slots as a GPU holder, granted at once, even over the pool, so a job that holds the GPU never waits for a CPU slot and cannot deadlock with a job that holds a slot and waits for the GPU. (The lock alone gave the GPU to whichever waiter polled first, so a job could be passed for an hour.) A scheduler of an older checkout has no turns; `run --gpu` then waits for the lock directly, as before. Any command that uses the GPU (`just test-category Runtime`, a `dotnet test` of a GPU suite, a benchmark) runs with `--gpu`, and only such a command: a CPU suite under `--gpu` holds the GPU from the jobs that need it, and `run --gpu` prints a hint (it still queues) when every test project the command names sets `<GSharpTargetDialect>Cpu</GSharpTargetDialect>` in its csproj, as `Kassyi.GSharp.Tests.Cpu` does; `gpu-lock.js` alone is no longer called directly. `just fuzz-diff`, `just long-checks` and `fuzz-differential.js` take the GPU lock themselves for their GPU steps: queue them without `--gpu` (`run --gpu` refuses them), or the inner lock waits forever for the outer one. `gpu-lock.js` sets `GSHARP_GPU_LOCK_HELD` for the command it runs, and a `run --gpu` inside it (a `just` recipe that `long-checks.js` runs under the lock) does not take the lock again. Every `run` inside such a command, with `--gpu` or not, counts as the GPU holder's job and is granted at once, like the jobs of `--gpu`.
- A slot follows the command: when the client is killed but its command runs on (a tool timeout that kills only the client), the scheduler keeps the slot until no process of the command is left. A cancelled job exits with 4 once its command has stopped; its slot is held until then. A command that had already ended with 0 by itself when the cancel reached it succeeded: `run` exits with 0. After a scheduler restart, running jobs keep their slots from the state file and their clients re-register; only when the state file is missing (or was written by an older scheduler) is nothing granted for the first 1.5 s. Jobs keep their ids, so a `cancel <id>` read from an earlier `status` never hits another job, and `cancel` reports only the jobs it really cancelled (not one that ended meanwhile).
- The scheduler (127.0.0.1:47117, log `tmp/job-queue/server.log` of the main checkout, also its working directory) starts on the first `run` and exits after 30 idle minutes. On Windows it is started through WMI, outside the caller's job object: Antigravity ends every process of a command when the command ends, which would take a scheduler started as a plain child with it. `job-queue.js stop` stops it; running jobs keep running and re-register, and the next client to connect starts the next scheduler from its own checkout, so after a change to the script, stop it from a checkout with the new version and run a job from there first. A job whose client was already lost is restored from `jobs-<port>.json` next to the log. Clients and schedulers of different checkouts work together for plain runs (protocol 2); `move`, `set-weight`, `--after` and a moved job need a scheduler of protocol 3, and an older one refuses them with a message to stop it.
- `cancel-all` reaches every job the scheduler knows, `--gpu` jobs waiting for their turn included. A run of `gpu-lock.js` outside the queue (`just fuzz-diff`, `just long-checks`) is not a job: stop it with Ctrl+C or by its process.
- The command runs in the shell `run` is called from, so write it as for that tool: Git Bash on Windows when `MSYSTEM` or `SHELL` is set (the Claude Code Bash tool), PowerShell otherwise on Windows (the Claude Code PowerShell tool, Antigravity; a quoted program path needs `&`), `/bin/sh` elsewhere. `--shell bash|pwsh|powershell|cmd|sh` chooses one. PowerShell passes the exit code of the last native program on. Pass the command as one quoted string; several words after `--` are taken as arguments already split by your shell and are quoted again one by one, so `&&`, pipes and redirections among them are not shell syntax. Limits of that re-quoting: cmd still expands `%VAR%` inside quotes, PowerShell cannot pass a literal `--%` on (`run` stops with a usage error), and Windows PowerShell 5.1 (used only when PowerShell 7 is missing) drops embedded `"` from arguments.
- A command run by a queued job that calls `run` again runs at once, without a second slot, with the same node limit.
- A PreToolUse hook (`check-queued-command.js`) denies these commands when they do not go through the queue, in Claude Code (`.claude/settings.json`) and in Antigravity (`.agents/hooks.json`). Text that only names such a command passes when it is quoted or in a heredoc; the hook reads quotes as the tool's shell does (Git Bash for the Claude Code Bash tool, PowerShell for its PowerShell tool and for Antigravity), and a `$( )` or PowerShell `@( )` substitution or `$x = dotnet test` is a command. It also sees through `wsl`, `cmd /c`, `pwsh -Command`, `bash -c` and programs that run a command given in their arguments (compute-sanitizer, valgrind, a program held in a variable); `just --dry-run`, `--help` / `--dry-run` of the scripts and `gpu-lock.js --lock-path` pass. It cannot see a command held in a variable and run later, or the contents of a script file. Other agents follow this section.
- In Claude Code the hook queues a plain command instead of denying it: segments joined by `&&` only, each a command the hook allows (`cd x`, `git ...`) or a bare `dotnet build` / `test` / `publish` / `pack` / `vstest` / `msbuild`, `msbuild` or `just <recipe>` (bash environment assignments before it allowed), run from a directory that holds `scripts/human/job-queue.js`. The tool then runs `node scripts/human/job-queue.js run [--gpu] [--weight <n>] --shell bash|pwsh -- '<command>'` (the command in single quotes of the tool's shell, a trailing `# intent:` comment kept outside them), with the rest of the tool input unchanged and no permission decision, so the permission prompt still applies to the queued command, and the agent is told so. `--gpu` is added when a named test project sets `<GSharpTargetDialect>Cuda</GSharpTargetDialect>`, left out when every named one sets `Cpu`, and a `just` recipe gets the options it passes to the queue itself in the `justfile`. When that cannot be told (`dotnet test` naming no project of `tests/`, a project with no dialect, a recipe that chooses its options from its arguments, an MSBuild test target), the command is denied with a sentence saying that it may need `--gpu`. Everything else stays denied as before: other separators, line breaks, heredocs, here-strings, substitutions and backticks, input redirections, groups, assignments, launch prefixes, wrappers, the long test scripts, `gpu-lock.js`, `dotnet watch`, Stryker, a recipe after a change of directory, PowerShell's `--%`, a command Git Bash would turn into a Windows path (`/x...`, `X=/x...`), a command that already runs the queue, and every Antigravity command.
- A wait can be long; run a queued command in the background when the tool has a time limit.
