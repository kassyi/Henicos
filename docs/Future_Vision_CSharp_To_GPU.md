# Future Vision: G# AOT + JIT Hybrid Architecture

## 1. 究極のゴール (The Ultimate Goal)

G# (`Kassyi.GSharp`) の真の価値は、「実行時に文字列を組み立ててGPUを動かすこと」ではなく、**「開発者が標準的な C# の文法で書いた数学的アルゴリズムが、ビルドした時点で自動的に最高速のGPUネイティブコードへ変換されていること」**にあります。

プログラマは、GPUのメモリ管理やスレッドの同期、レジスタの枯渇などを一切意識することなく、以下のように純粋なC#コードを書くだけです。

```csharp
[GpuKernel]
public static void FermatLoop(uint[] T, int E)
{
    for (int i = 0; i < E; i++)
    {
        // 複雑な多倍長演算ロジック
    }
}
```

## 2. 哲学: Do's and Don'ts

G# は「C#で記述されたロジックを、CUDA C++へトランスパイルしてGPU上で超高速実行する」ための専用サブセットおよびトランスパイラです。
以下に、G#が目指す方向性（Do）と、意図的にサポートを捨てる領域（Don't）を定義します。

### ✅ Do's (目指すこと・やること)
1. **「C#をシェーダー言語として扱う」**: 既存のC#の文法やIDEの支援（リファクタリング、構文解析）をフル活用し、GPUカーネルを記述できるようにする。
2. **「HPC・数学演算への特化」**: 多倍長整数演算（BigInt）、暗号処理、機械学習の行列演算など、スレッド並列性が活きる計算処理にフォーカスする。
3. **「IL（中間言語）ベースのトランスパイル」**: Roslynによるソースコード解析ではなく、`Mono.Cecil` を用いたIL解析を行う。これにより、高度な最適化済みの命令を元に生成でき、将来的にはF#など他の.NET言語のサポートも可能になる。
4. **「人間が読めるクリーンなCUDA C++の生成」**: 出力されるC++コードはデバッグ可能であり、NVCC等で簡単にJITコンパイルできるようにする。
5. **「静的メモリ・ポインタ演算のサポート」**: パフォーマンスのために `ref` / `out` やスタックベースのポインタ演算（`&`, `*`）を積極的にサポートする。

### ❌ Don'ts (やらないこと・サポートしないこと)
1. **「完全な .NET ランタイムのGPU上でのエミュレート」**: ガベージコレクション (GC) は実装しない。GPU上での `new object()` やクラスのインスタンス化はサポートしない（ヒープアロケーションの禁止）。
2. **「動的ディスパッチとリフレクション」**: インターフェース経由の呼び出し、仮想メソッド（`virtual` / `override`）、実行時リフレクションなど、静的に解決できない処理は禁止する。
3. **「リッチな標準ライブラリのサポート」**: LINQ、文字列操作（`string`）、動的コレクション（`List<T>` など）のサポートは行わない。データは常にプリミティブ型の配列や固定長構造体として扱う。
4. **「トランスパイラ自体での実行時リフレクションの多用」**: AST構築等のトランスパイル処理そのものは高速であるべき。遅延の原因となる実行時リフレクション（`System.Reflection`）は原則避け、`Mono.Cecil` で静的に解析する。

## 3. AOT + JIT ハイブリッドアーキテクチャ

G# が最終的に目指すアーキテクチャは、.NET の NativeAOT や Dynamic PGO の思想を受け継いだ **「AOT（事前コンパイル）と JIT（実行時最適化）のハイブリッド」** です。

### AOT（プリコンパイル）層によるゼロオーバーヘッド化

ビルド時に **Roslyn Source Generator** を活用し、`[GpuKernel]` 属性が付与されたメソッドのSyntax Tree（またはIL）を静的に解析します。

- 実行時のIL解析やリフレクションのオーバーヘッドを完全に排除します。
- 開発者がVisual Studioでコードを書いている最中に、不正なGPUコード（サポートされていないクラスのインスタンス化など）があれば、即座にコンパイルエラー（赤い波線）として警告します。
- C#コードから等価な **CUDA C++ のソースコード文字列** を、ビルド時に自動生成してDLLに埋め込みます。

### JIT（環境適応）層による極限の最適化

GPUコンピューティングにおいて、AOTだけで「すべての環境で最速のバイナリ（Fatbin）」を出力することは不可能です。そのため、G# は実行時に一度だけJITコンパイル（nvccの動的起動）を行います。

- **アーキテクチャ特化 (SM Versions)**: 実行マシンのGPU世代（例: Turing `sm_75`, Ampere `sm_86`, Hopper `sm_90`）を動的に判定し、そのシリコンの能力を100%引き出すPTXをコンパイルします。
- **動的定数によるレジスタ削減**: `E` やスレッドブロックサイズなど、実行時にしか判明しないパラメータを「定数（Constant）」としてコードジェネレータに注入し、`#pragma unroll` を活用した強力なループ展開を行います。これにより、GPUの死活問題であるレジスタ消費量を激減させます。
- **キャッシュ機構**: 一度JITコンパイルされた専用のネイティブDLLはキャッシュされ、次回以降の実行では即座にロードされます。

## 4. 今後のロードマップへの影響

現在、我々が構築しているのは **「JITコンパイル基盤」と「ILからのAST構築基盤」** です。AST構築、算術・論理演算、インライン展開、ポインタ・参照機能（フェーズ1〜4）は順調に完了しました。

今後は「より複雑なデータ構造のサポート」と「GPUアーキテクチャ特有の機能」へ移行し、最終フェーズとして **Roslyn Source Generator を用いたAOT層への移植** を行います。

### 📍 フェーズ 5: 完全な型システムと構造体 (Type System & Structs)
現状、C++出力時のローカル変数は一律 `int` になっています。これを解決し、多様なデータを扱えるようにします。
- **ローカル変数の型推論**: ILの `VariableDefinition` やスタックの状態から、`ulong`, `float`, `double` 等を判別し、正しいC++型 (`unsigned long long`, `float` 等) で宣言を出力する。
- **値型構造体 (`struct`) のサポート**: C#の `struct` をC++の `struct` にマッピングし、値渡しやフィールドアクセス (`Ldfld`, `Stfld`) をサポートする。

### 📍 フェーズ 6: 制御フローの完全化 (Advanced Control Flow)
- **`switch` ステートメント**: `Switch` オペコードを解析し、C++の `switch-case` 文へ変換する。
- **短絡評価 (`&&`, `||`) の厳密な再現**: C#の論理演算における短絡評価（ILレベルでの複雑なジャンプ命令）を、CFG（制御フローグラフ）を用いて最適化されたC++の条件式に再構築する。

### 📍 フェーズ 7: CUDA組み込み関数のサポート (CUDA Intrinsics)
GPUならではのハードウェアレベルの高速化命令をC#から呼び出せるようにします。
- **組み込み関数のマッピング**: C#側にダミーの静的メソッド（例: `__syncwarp()`, `__popc()`）を用意し、トランスパイラがこれを直接CUDAの組み込み関数へと置換する機構の実装。
- **Shared Memory (`__shared__`) のサポート**: 特定の属性が付与された配列を、CUDAの共有メモリとして割り当てる構文の追加。

### 📍 フェーズ 8: カーネル起動とエコシステムの統合 (Launch & Tooling)
- **C#からの透過的なカーネル起動**: `BackendCompiler` と連携し、C#のメソッド呼び出しのように自然にGPUカーネルを起動できるラッパーコードの自動生成。
- **Source Generator化の完了**: 実行時のJITコンパイルだけでなく、ビルド時にRoslyn Source GeneratorでC#コードからC++コードとC++呼び出し用P/InvokeのDLL・C#側のラッパーを生成する基盤を作る。

### 🚀 その先の展開: PTXインメモリ実行エンジンの実験
Phase 8までの基盤（AST生成からC++トランスパイルまで）が安定した後、**「NVIDIA Driver APIを用いたPTX実行エンジンの実験」**を開始します。
これは `nvcc` で生成したPTX文字列をディスク（DLL等）を介さずにRAM上で直接GPUにロード・実行する機構であり、これによってI/Oボトルネックやデータ実行防止機能の制約を完全に排除した「真のオンザフライJITコンパイル」への進化を目指します。

すでにGSharpは独立したコンポーネントとしてパイプライン分離されており、このハイブリッドアーキテクチャへの移行準備は整っています。
