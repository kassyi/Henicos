| :--- | :--- | :--- | :---: | :---: | :--- | :---: | :--- |
| **GBI-01** | メモリ管理 | **`GSharpJitProvider` のメモリプール不在** | - [ ] | - [ ] | `AllocateMemory` / `FreeMemory` が直接 `cuMemAlloc` / `cuMemFree` を発行。`DivRem` や `ModPow` など内部で大量のテンポラリを生成・破棄する処理で深刻なレイテンシ（数秒〜数十秒の遅延）が発生する。 | **Tier 2** (28) | `GpuContext` または Provider レベルでスラブアロケータ / テンポラリバッファ再利用プールを実装し、反復計算中の `cuMemAlloc` をゼロ化する。 |
| **GBI-02** | テスト | **`Test_ModPow_Correctness` の Skip 解消** | - [x] | - [ ] | `ModPow`（バイナリ累乗法）のアルゴリズム自体は実装済みだが、GBI-01 のアロケーション遅延を回避するため一時的に `[Fact(Skip)]` に設定されている。 | **Tier 3** (27) | GBI-01 のメモリプール実装後、テストを実行して検証・有効化する。 |
| **GBI-03** | パフォーマンス | **CPU-Fallback メソッドの GPU リダクション化** | - [ ] | - [ ] | `CompareTo`, `GetBitLength`, `IsZero`, `IsOne`, `IsEven` 等が `CopyDeviceToHost` で全ワードを CPU に転送して判定している。 | **Tier 2** (29) | GPU 側で並列リダクションカーネルを実行し、最終結果（1ワード/真偽値）のみをホストへ返却するよう改修。 |
| **GBI-04** | 演算最適化 | **`Square` 専用 JIT カーネルのディスパッチ** | - [ ] | - [ ] | 現在 `GSharpJitProvider.Square` は汎用の `Mul(A, A, Result)` を呼び出して代用中。Native 側には存在する専用二乗ルーチン（`Device_NTT_PointwiseSquare`）が JIT 側でバイパスされている。 | **Tier 2** (28) | JIT 側でも二乗専用の Pointwise カーネルを直接ディスパッチし、NTT 変換回数および乗算計算量を半減させる。 |
| **GBI-05** | 演算最適化 | **Lehmer's GCD の大桁並列化** | - [x] | - [x] | 現在の GCD 実装は単一ブロック/少数スレッドでの逐次商推定に依存しており、超巨大桁（数万〜数十万ワード）時のスケーラビリティに限界がある。 | **Tier 4** (11) | Half-GCD / Matrix-based GCD の並列 GPU 実装を検討。 |
| **GBI-06** | 実行基盤 | **式木（`GpuBigIntExpr`）の Kernel Fusion** | - [ ] | - [ ] | 現在の式木は個別カーネル（Add, Sub, Bitwise 等）を直列ディスパッチしており、中間バッファの VRAM 読み書き帯域を消費する。 | **Tier 4** (15) | 複数の要素別演算を動的 JIT で 1 つの CUDA カーネルに融合（Kernel Fusion）してディスパッチする仕組みを導入。 |
