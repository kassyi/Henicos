# GSH0008: LINQ is not allowed in GPU kernels

## Details

| Property | Value |
| :--- | :--- |
| **Diagnostic ID** | GSH0008 |
| **Category** | GSharpTranspiler |
| **Severity** | Error |
| **Enabled by Default** | Yes |

## Why This Rule Exists (Architectural Context)

### Closure Allocations, Delegates, and GPU State Machines
Language Integrated Query (LINQ) is one of C#'s most expressive features, but its internal mechanics are entirely incompatible with GPU architectures:

1. **Delegate Closures**: LINQ operations (e.g. `.Where(x => x > 0)`) allocate delegate objects (`Func<T, bool>`) and closure classes on the managed heap to capture state.
2. **State Machine Overhead**: Methods like `.Select()` use iterator state machines (`yield return`) with complex jump tables that destroy SIMT thread synchronization.
3. **Dynamic Dispatch**: LINQ operates through interface dispatch (`IEnumerable<T>`), which prevents the CUDA compiler from inlining functions into GPU registers.

## Cause

LINQ query syntax (`from ... in ... select`) or LINQ extension methods (`.Where()`, `.Select()`, `.Aggregate()`, etc.) were used in device code.

## How to Fix

Replace LINQ queries with explicit imperative `for` loops or parallel grid-stride loops.

## Examples

### Code with Warning / Error (Before)

```csharp
// Execution Context: G# Kernel (GPU)
[GpuKernel]
public static void BadKernel(float[] data)
{
    // Error GSH0008: LINQ extension methods rely on delegates and heap allocations
    var positive = data.Where(x => x > 0.0f);
}
```

### Corrected Code (After)

```csharp
// Execution Context: G# Kernel (GPU)
[GpuKernel]
public static void GoodKernel(float[] data, float[] output, int length)
{
    int tid = ThreadIndex.X + BlockIndex.X * BlockDimension.X;
    // Correct: Explicit imperative condition evaluated directly in thread registers
    if (tid < length && data[tid] > 0.0f)
    {
        output[tid] = data[tid];
    }
}
```
