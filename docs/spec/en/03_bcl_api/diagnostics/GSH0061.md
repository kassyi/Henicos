# GSH0061: Kernel overloads cannot be told apart by their launch wrappers

## Details

| Property | Value |
| :--- | :--- |
| **Diagnostic ID** | GSH0061 |
| **Category** | GSharpCompiler |
| **Severity** | Error |
| **Enabled by Default** | Yes |

## Why This Rule Exists (Architectural Context)

`[GpuKernel]` methods can be overloaded. Each overload gets its own device entry point, and the host wrappers are chosen by C# overload resolution:

- `Launch{Kernel}` takes the same parameter types as the kernel.
- For an overloaded kernel, `Launch{Kernel}Ptr` takes every array-like and `ref` / `out` parameter as a typed `GpuBuffer<T>` and passes its device pointer to the kernel.

Some overloads that C# can tell apart become identical in a wrapper. For example, `int[] data` and `ref int value` are both a `GpuBuffer<int>` in `Launch{Kernel}Ptr`, and `in int x` and `int x` are both `int x` in `Launch{Kernel}`. G# reports the conflict instead of generating wrappers that do not compile. The wrapper is checked on every dialect, so that the same source builds for both CPU and CUDA.

## Cause

Two `[GpuKernel]` overloads in the same type map to the same `Launch{Kernel}` or `Launch{Kernel}Ptr` parameter list. The second overload gets no host wrappers.

## How to Fix

Give one of the kernels a different name.

## Examples

### Code with Error (Before)

```csharp
public static partial class Kernels
{
    [GpuKernel]
    public static void Fill(int[] data) { data[ThreadIndex.X] = 1; }

    [GpuKernel]
    public static void Fill(ref int value) { value = 2; } // ❌ GSH0061: both are Fill(GpuBuffer<int>) in LaunchFillPtr
}
```

### Corrected Code (After)

```csharp
public static partial class Kernels
{
    [GpuKernel]
    public static void Fill(int[] data) { data[ThreadIndex.X] = 1; }

    [GpuKernel]
    public static void FillOne(ref int value) { value = 2; } // ✅
}
```
