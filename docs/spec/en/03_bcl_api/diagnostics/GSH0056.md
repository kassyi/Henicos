# GSH0056: GPU method name is a C++ keyword (Deprecated)

> [!WARNING]
> **Deprecated Diagnostic**
> This diagnostic is no longer reported by the compiler. Method names are now renamed automatically ([#402](https://github.com/kassyi/Henicos/issues/402)): a `[GpuKernel]` or `[GpuDeviceFunction]` method named after a C++ keyword compiles without changes.

## Details

| Property | Value |
| :--- | :--- |
| **Diagnostic ID** | GSH0056 |
| **Category** | GSharpTranspiler |
| **Severity** | Error |
| **Enabled by Default** | No (retired) |

## Why This Rule Exists (Architectural Context)

### Method Names Were Emitted Verbatim
The transpiler derives the C++ name of every parameter, local variable, label, local function, lambda parameter and struct member from its symbol, so these could always use any legal C# name, including C++ keywords such as `register`, `template`, `union` or verbatim identifiers such as `@class`.

Method names live in the C++ global scope, where the transpiler used to emit them verbatim. A method named after a C++ keyword produced a C++ syntax error that NVRTC, nvcc, or the host C++ compiler reported against the generated file, far away from the C# source, so this diagnostic rejected such names at the C# declaration.

Global names are now derived from the full C# path of the declaration (`__gsharp_fn_{type path}__{name}` for a device function, `__gsharp_k_…` for a kernel), so a keyword is an ordinary name and the check is gone.

## Cause

The name of a `[GpuKernel]` or `[GpuDeviceFunction]` method is a C++20 keyword or alternative operator token (`and`, `or`, `not`, `xor`, ...). Verbatim identifiers such as `@class` are reported too, because their C# name is the bare keyword.

## How to Fix

Nothing: the name is accepted. The host wrapper keeps the C# name, for example `Launchtemplate` for a kernel `template`.

## Examples

```csharp
// Execution Context: G# Kernel
[GpuDeviceFunction]
public static int template(int register) => register * 2; // ✅ accepted
```
